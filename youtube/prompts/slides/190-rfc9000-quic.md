## Slide 1: Introduction to QUIC Protocol
- QUIC (Quick UDP Internet Connections) is a modern transport protocol developed at IETF
- Designed to replace TCP for HTTP/3 and other applications requiring secure transport
- RFC 9000 published in May 2021 as the foundational specification
- Built on UDP instead of TCP to enable faster deployment and innovation
- Integrates TLS 1.3 security directly into the transport layer

## Slide 2: QUIC vs TCP - Architecture Comparison
- QUIC operates on top of UDP protocol layer, not IP directly like TCP
- Eliminates head-of-line blocking present in TCP by using independent streams
- Combines transport and encryption in a single handshake (1-RTT or 0-RTT)
- TCP requires separate TLS handshake adding latency (2-3 RTTs minimum)
- QUIC can multiplex multiple streams over a single connection without blocking

## Slide 3: Connection Establishment Speed
- Traditional TCP + TLS requires 2-3 round-trip times (RTTs) to establish secure connection
- QUIC reduces this to 1-RTT for initial connections with full handshake
- 0-RTT resumption allows immediate data transmission for returning clients
- Connection migration supported - can survive IP address or port changes
- Faster page load times especially on high-latency networks

## Slide 4: Connection Identifiers
- QUIC uses unique Connection IDs instead of 4-tuple (src IP, src port, dst IP, dst port)
- Enables connection migration when network changes (WiFi to cellular, NAT rebinding)
- Connection ID is negotiated during handshake and can be rotated
- Multiple Connection IDs can be active simultaneously for smooth transitions
- Critical for mobile devices and long-lived connections

## Slide 5: Encryption by Default
- Nearly everything in QUIC packets is encrypted using TLS 1.3
- Only minimal header information visible: version, connection ID, packet number
- Packet numbers are always encrypted to prevent tracking and manipulation
- Much stronger privacy compared to TCP where headers are plaintext
- Prevents ossification - middleboxes cannot inspect and interfere with protocol evolution

## Slide 6: Mitigating Amplification Attacks
- QUIC limits amplification risk through simple anti-amplification rules
- Server cannot send more than 3x the data received before address validation
- Address validation proves client controls the claimed IP address
- PATH_CHALLENGE and PATH_RESPONSE frames validate new paths
- Critical defense against DDoS reflection attacks using UDP

## Slide 7: Loss Detection and Recovery
- QUIC uses ACK frames that report received packet ranges
- Packet numbers are strictly increasing and never reused (unlike TCP sequence numbers)
- RTT (Round-Trip Time) measurement is more accurate than TCP
- Separate packet number spaces for different encryption levels
- Supports multiple congestion control algorithms

## Slide 8: Stream Multiplexing
- Multiple independent data streams within single QUIC connection
- Stream-level flow control prevents any stream from monopolizing bandwidth
- No head-of-line blocking between streams (unlike HTTP/2 over TCP)
- Bidirectional and unidirectional streams supported
- Stream IDs assigned by initiator with client-server separation

## Slide 9: Key Lessons from RFC 9000
- IETF learned from decades of TCP deployment challenges and ossification
- Built-in encryption makes QUIC easier to evolve without middlebox interference
- UDP substrate allows deployment without requiring kernel updates
- Version negotiation designed into protocol from day one
- Separating transport concerns from application protocol (HTTP/3)

## Slide 10: QUIC Evolution and Future
- Version 1 (RFC 9000) establishes solid foundation but not the final word
- Extension mechanisms allow new features without breaking existing deployments
- Already seeing adoption in HTTP/3, DNS over QUIC, and other protocols
- Designed to evolve rapidly compared to TCP's 40+ year ossification
- Focus on getting version 1 stable first, then iterate on improvements
